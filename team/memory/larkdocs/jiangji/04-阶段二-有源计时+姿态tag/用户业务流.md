# 星际骑遇 · 用户业务流设计（端 → 场地 → 云 → 小程序）

> 本文基于**当前已实现的硬件与软件**梳理一条完整的用户业务流，覆盖：①新用户绑定设备 ②老用户入场签到 ③场地器件摆放与端云配合 ④用户数据分析与展示。  
> 依据：`solution-phases/ref-timing-phase1-2/solution-final.md`（有源 Tag 方案）、`/docs/app-ble-protocol.md`（BLE 协议）、`.claude/CLAUDE.md` 决策 A/B、以及 `cycling/`（小程序 + 云函数 `device.js`）现状。  
> 术语：**Tag**=车载标签（我方 ESP32-S3 + Si3933 + IMU）；**激励器**=125kHz LF 发射器 + 地感线圈（铺过线点）；**基站**=固定安装的 ESP32 + 4G，收 Tag 的 ESP-NOW 并上云。

---

## 0. 角色与设备总览（先对齐）

| 角色 | 硬件 | 职责 | 归属 |
|-|-|-|-|
| **车载 Tag** | ESP32-S3 + Si3933(LF唤醒) + ICM-42688(IMU) + BMP280 | 过线微秒时间戳锁存、姿态/腾空/速度边缘解算、ESP-NOW 上行、BLE 与小程序交互（标定/绑定/看数据） | 用户随车（一车一 Tag） |
| **过线激励器** | 125kHz 激励器 + 地感线圈 | 在过线点持续发射 LF 唤醒场，Tag 进入即被唤醒 | 场地固定（起点/终点各一，**不同唤醒码/ID**） |
| **过线基站** | ESP32 + 4G(Cat.1) | 汇聚 Tag 的 ESP-NOW 包（时间戳/姿态遥测）→ 4G 上云；断网 SPIFFS 缓存补传 | 场地固定（市电供电） |
| **云端** | 腾讯云 COS + SCF + 数据库 | COS 收原始上报 → SCF 按 `tag_id→user_id` 路由 → 入库 → 推送小程序 | 我方自研 |
| **小程序** | 微信小程序（用户端/教练端/管理员端） | 绑定设备、看成绩/姿态、标定、签到辅助 | 我方自研 |

**关键决策约束**（不可推翻）：

- **时间戳在 Tag 的 LF 唤醒中断里本地锁存（微秒）**，不用基站收包时刻当过线时刻（决策 A2/G28）。
- **两点位**（起点+终点，不同唤醒码）优于单点（决策 A3）。
- 只用供应商 LF 唤醒芯片，**不用其封闭成品标签**；2.4G 上行用我方 ESP-NOW（决策 B5/B6）。
- 联网 = **基站 + 4G** 聚合上云，Tag 只走 ESP-NOW（决策 17b）。

## 1. 首次新用户入场 —— 绑定设备

目标：把"一台物理 Tag"唯一绑定到"一个用户账号"，此后只有机主能看自己的数据、标定自己的车。

### 1.1 现状（小程序 + 云端已实现）

云端 `devices` 集合已有：`purchaseDevice`（购买建索引）、`activateDevice`（用 `adminKey` 建立"用户↔设备"唯一联系）、`getMyDevice`。设备侧固件已有 `CMD_BIND`（写 16B `owner_token`）+ 绑定可见性规则（未绑定先到先得；已绑定仅机主 `owner_token` 可解锁看数据；管理员可强制解绑）。

### 1.2 完整绑定流程（首次）

```
① 用户到店领/购 Tag（车上已装好，机身/包装印有 adminKey + 二维码）
        ↓
② 微信扫码进小程序 → 登录（手机号/微信授权）→ 我的设备
        ↓
③ 购买/领用：purchaseDevice → 云端建 devices 记录(status=unactivated)
        ↓
④ 激活：输入机身 adminKey → activateDevice
     - 云端校验 adminKey 全局唯一 → 绑定 ownerPhone↔device，status=active
     - 云端生成/下发 16B owner_token（账号体系派发）
        ↓
⑤ 进入【设备管理】→ 搜索设备 → 自动连接（BLE）
     - 读 ST_INFO（tag_id/固件/绑定状态）
     - 设备未绑定 → 小程序用 owner_token 发 CMD_BIND → 设备落 NVS，返回 BIND_RES ok
     - owner_token 本地安全存储（换手机重新登录从云端取回）
        ↓
⑥ 首次标定（设备管理 → 姿态系统）：
     - 陀螺标定（静置 ≥10s，落 NVS）
     - 加计六面标定（引导 + 放置检测，6 面各 ≥10s，落 NVS）
     - 断电重启自动从 NVS 加载（已实现：app_main 开机 calib_nvs_load）
        ↓
✅ 绑定完成：user_id ↔ tag_id ↔ owner_token 三者建立映射（云端 tag_bindings）
```

### 1.3 云端映射（绑定的本质）

```
tag_bindings ( tag_id PK, user_id, owner_token_hash, bind_time, status )
```

这张表是后续所有数据"按 tag_id 路由到正确 user_id"的核心——过线记录只带 `tag_id`，云端靠它找到人。

> ⚠️ 待补齐（当前 gap）：现有 `device.js` 用 `adminKey` 建立"用户↔设备"，但**尚未落地 `owner_token` 的云端下发 + `tag_id→user_id` 路由表**。绑定要真正闭环，需新增：`generateOwnerToken`（激活时派发）+ `tag_bindings` 路由集合。见第 5 节"待落地清单"。

## 2. 老用户每次入场 —— 签到

目标：用户到场后系统自动认出他，开始记录本次训练；**无需每次手动操作**。

### 2.1 签到方式（按优先级，已在集成文档定调）

| 方式 | 机制 | 优点 | 定位 |
|-|-|-|-|
| **① LF 过线门（主）** | 骑过起点激励器 → Tag 被 125kHz 唤醒 → 锁存微秒时间戳 → ESP-NOW 报基站 → 云端按 tag_id 认人 | 全自动、准、天然就是计时点 | **主方案** |
| **② BLE 邻近（辅）** | 小程序在场地连上自己的 Tag（RSSI 邻近）即视为签到 | 无需过线也能签到（热身区） | 辅助 |
| **③ 扫码（兜底）** | 扫场地码/车上码手动签到 | 设备异常时兜底 | 兜底 |

### 2.2 老用户入场自动签到流程

```
① 用户到场（Tag 已绑定、已标定，开机）
        ↓
② Tag 自动进入低功耗待机，ESP-NOW 待命
        ↓
③ 骑车经过【起点激励器】→ Tag LF 唤醒中断锁存 t_us + 起点码
        ↓
④ Tag 经 ESP-NOW 发 {tag_id, t_us, point=start, lap} 给基站
        ↓
⑤ 基站 4G 上云 → COS → SCF 查 tag_bindings(tag_id→user_id)
        ↓
⑥ 云端判定：该 user_id 今日首次过线 = 自动签到 → 建一条 session（本次训练）
        ↓
⑦ 小程序推送"已签到，开始记录"（订阅消息/WebSocket）
        ↓
后续每圈：起点→终点→起点 计一圈，圈速 = 终点 t_us − 起点 t_us（同一 Tag 的两次微秒时间戳之差，精度 ms 级）
```

**为什么准**：圈速是**同一个 Tag 的两个本地微秒时间戳相减**，不受无线传输抖动影响（决策 A2）。基站/云只负责搬运和归属，不参与计时。

> 签到 ≈ "本次训练 session 的开始"。云端用 `session(user_id, date, start_ts, ...)` 表承接；同一天多次入场可按时间间隔切分多个 session。

## 3. 场地器件摆放 + 端云配合

### 3.1 场地布局（环形泵道，两点位）

```
                    [终点激励器+地感线圈]  ← 唤醒码 B / exciter_id=2
                          ╱──────────╲
                         ╱            ╲
        泵道赛道 →      │              │
                         ╲            ╱
                          ╲──────────╱
                    [起点激励器+地感线圈]  ← 唤醒码 A / exciter_id=1
                          │
                    [过线基站 ESP32+4G]  ← 立杆/门架，市电，覆盖全场 ESP-NOW
                          │
                          ↓ 4G
                        [云端]
```

**摆放要点**：

- **激励器/地感线圈**：贴地铺设在过线断面，**薄、无凸起、全非金属防护**（决策 20），灌封后调谐到 125kHz。触发区调窄（0.5m 档）→ 过线点精准。
- **起点/终点两个激励器设不同唤醒码 + 不同 exciter_id**（决策 A3）——Tag 据此区分过的是起点还是终点。
- **基站**：立杆/门架固定，市电供电，WROOM-1U + 外置增益天线或双基站分区覆盖 40×60m 全场（决策 17d）；一个基站即可收全场 Tag 的 ESP-NOW。
- **供电**：激励器可市电/内置电池；基站市电 + 4G 物联网卡。

### 3.2 端云配合获取用户信息（完整数据链）

```
[车载 Tag]
  ├ LF 唤醒：过线微秒时间戳 t_us（计时核心）
  ├ IMU 边缘解算：姿态(roll/pitch/yaw) + 腾空(airtime/高度) + 速度（每圈锚点校准）
  └ ESP-NOW 上行 {tag_id, t_us, point, lap, odom...}   50-200Hz
        ↓ 2.4G ESP-NOW（<10ms）
[过线基站]
  ├ 汇聚所有 Tag 的包（各 Tag 用 tag_id 区分，互不冲突）
  ├ 断网 SPIFFS 缓存，恢复后补传
  └ 4G 上云
        ↓ HTTPS PUT
[① 腾讯云 COS]  raw/{date}/{station}/{ts}.json  （原始上报，留痕可回放）
        ↓ 对象创建事件触发
[② 云函数 SCF]  查 tag_bindings(tag_id → user_id) 路由；未绑定 → unbound 待认领
        ↓
[③ 数据库（按 user_id 隔离）]
   users / tag_bindings / sessions / crossings / laps / telemetry
        ↓
[④ 推送]  MQTT / WebSocket / 微信订阅消息  → user/{user_id}/...
        ↓
[小程序]  实时圈速 + 姿态回放 + 排行榜
```

**两条信息通道（勿混）**：

- **骑行遥测**（圈速/姿态/腾空）：Tag → **ESP-NOW** → 基站 → 4G → 云（无手机参与，决策 11 只传 odom 状态量，不传原始 IMU）。
- **标定/查看/绑定**：Tag ↔ **BLE** ↔ 小程序（静止近距离，手机直连）。

### 3.3 现有固件已具备的数据（可直接用）

- 过线：`ST_CHECKIN {t_us, point(起0/终1), lap}`。
- LF 调试/RSSI：`ST_LF_DEBUG {signal, rssi[3], base_id, mag}`（触发系统面板 + 峰值判最近）。
- 遥测快照：姿态、垂直速度、腾空 ms/高度、位置。
- 飞行记录器：IMU 100Hz + baro + 解算 + **LF 触发**（`LOG_REC_LF`）落盘，可事后下载分析。

## 4. 用户信息分析与展示（怎样最合理）

原则：**现场看即时反馈，事后看趋势成长**；数据都来自云端真实记录，无占位（决策数据真实性）。

### 4.1 数据分层

| 层级 | 数据 | 来源 | 展示时机 |
|-|-|-|-|
| **计时层** | 圈速、本圈/最佳/平均、圈数、排名 | crossings/laps | 现场实时 |
| **运动层** | 姿态曲线、过弯倾角、腾空次数/高度/时长、速度 | telemetry | 骑行中 + 回放 |
| **成长层** | 历史最佳趋势、周/月训练量、稳定性 | 聚合 sessions | 训练后/长期 |
| **社交层** | 排行榜、好友对比、场馆榜 | 跨 user 聚合 | 随时 |

### 4.2 展示建议（按场景）

**A. 骑行中（Tag→基站→云→小程序，准实时）**

- 大字**当前圈速** + 与个人最佳的差值（+/−）；
- 简易**姿态/倾角**指示（复用现有地平仪）；
- 腾空即时提示"腾空 0.8s / 高度 0.4m"。

**B. 单次训练结束（session 汇总）**

- 本次圈数、最佳圈、平均圈、总时长；
- **每圈明细**：圈速柱状 + 该圈最大倾角/腾空次数；
- **高光片段**：腾空最高/倾角最大的时刻（配合决策 14 视频事后裁剪，用时间戳对齐）。

**C. 长期成长（跨 session）**

- 最佳圈速**趋势曲线**（周/月）；
- 训练量热力图（哪天来、来几次、骑多久）；
- 稳定性指标（圈速方差下降 = 越骑越稳）。

**D. 社交/激励**

- 场馆排行榜（今日/本周最佳圈）；
- 好友/同门对比；
- 成就徽章（首次腾空、连续打卡、破个人纪录）。

### 4.3 分析方法

- **圈速**：同 Tag 相邻起点时间戳相减，异常值（掉圈/停留）按阈值剔除。
- **过弯倾角**：roll 峰值 + 对应速度 → 过弯能力画像。
- **腾空**：IMU airtime（0g 自由落体判定，H=g·T²/8，决策 C8）。
- **RSSI 峰值**（本次新增算法 A）：过线"最近点"判定，提升过线时刻精度。
- **重计算/AI 分析放云端**（决策 D13），Tag/基站只上报状态量，省带宽省电。

### 4.4 数据模型建议（在现有基础上补齐）

```
users        ( user_id PK, open_id, phone, nickname )
tag_bindings ( tag_id PK, user_id, owner_token_hash, status )   -- 路由核心
sessions     ( id PK, user_id IDX, venue_id, start_ts, end_ts, laps, best_lap_ms )
crossings    ( id PK, user_id IDX, tag_id, exciter_id, point, ts_us, rssi_peak, session_id )
laps         ( id PK, user_id IDX, session_id, lap_no, lap_ms, max_roll, air_count )
telemetry    ( id PK, user_id IDX, session_id, ts_ms, roll, pitch, yaw, vz, air_ms, height_mm )
```

## 5. 待落地清单（当前 gap，落地绑定/签到闭环所需）

> 硬件与 BLE/小程序设备管理已就绪；下列为让"业务流"真正跑通还需补的**云端**能力：

1. **owner_token 云端下发**：`activateDevice` 时生成 16B token 存 `tag_bindings`，下发小程序写设备（`CMD_BIND`）。
2. **tag_id → user_id 路由表**：`tag_bindings` 集合 + SCF 里的路由逻辑（现 `device.js` 只到 `adminKey↔ownerPhone`，缺 `tag_id↔user_id`）。
3. **⭐ 基站 4G 上云（第一优先级）**：`base/main/cloud_4g.c`（当前仅有 `cloud_wifi.c`）。**泵道现场建 WiFi 难 → 4G 是主方案，WiFi 仅调试兜底**。这是基站在真实场地能跑起来的前置项，排在最前。断网时 SPIFFS 缓存 + 恢复补传一并做。
4. **云端接入处理**：COS 桶 + SCF `process-crossing`（解析上报 → 路由 → 入库 → 推送）。
5. **sessions 自动切分**：按当日首次过线建 session，间隔阈值切分多次入场。
6. **签到事件推送**：订阅消息/WebSocket 通道，现场即时反馈。
7. **exciter_id ↔ 场地点位映射**：起点/终点/多场馆的激励器 ID 登记表。

> 阶段一（决策 24）先求走通：单场馆、单基站、起点+终点两激励器、**4G 上云**、圈速 + 基础姿态入库展示；社交/AI/视频高光按后续阶段扩展。  
> **优先级提示**：泵道侧 WiFi 建设成本/不确定性高，故 **4G(Cat.1) 上云提为第一优先级**（决策 17b），WiFi 降为桌面联调兜底。BOM 见 `/docs/phase1-debug/purchase-list.md` §二·四。
