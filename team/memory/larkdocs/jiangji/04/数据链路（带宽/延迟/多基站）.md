# 数据链路：带宽、延迟与多基站架构

> 回答一串工程问题：4G 上云够不够快？"开火车"20 人并发要多久到手机？多基站怎么分配负载？本文把这些定成**可落地的架构约束**，供 `base/main/cloud_4g.c`、Tag 上传逻辑、云端聚合开发直接参照。  
> 依据：决策 A2（时间戳 Tag 端锁存）、17b（基站+4G）、17d（多基站分区）、11（只传 odom 状态量）。上行包定义见《ESP-NOW 链路协议 · Tag → Base》。本文所有数字为工程估算，**上板实测后回填修正**。

---

## 0. 一句话结论（先看这个）

1. **月流量不是卡点。** 串口曾被误判为「上限 460800」——厂商手册上限实为 **921600**（DTU 指令手册『设置串口参数命令』，TTL 1200\~921600）。加上实测 log 校验（见 §八），**现有单基站透传 DTU 就够用（当前配置 230400，如需带宽可实测升到 921600）**。
2. **正解 = "双流分离"**：过线即发**几十字节摘要（实时流，秒级到手机）；整圈 200Hz 原始数据留 Tag flash 错峰补传（详细流，几十秒陆续到位，用户无感）。不要求大数据同时实时上传** —— 这直接消解并发瓶颈。
3. **单基站 + 双流分离，阶段一就够用。** 多基站是规模上去后的扩展优化，不是必需。
4. **多基站负载分配**：不是中心调度，而是**基站广播 queue 深度 + Tag 择空投递**（最短队列均衡，含防羊群）；且要认清**"整圈数据只在终点才完整，无法按起/终点点位切分"**。

## 1. 数据量与流量（月流量：够）

**要上云的不是"几十秒原始 log"**——原始全量 log 留在 Tag flash（调试经 BLE 拉），云端只要"每圈中间段"（决策 11）。

| 采样率 | 每样本 | 一圈(30s) 原始 | 说明 |
|-|-|-|-|
| 100Hz | 16B(t+acc3+gyr3) | \~48 KB | 姿态/圈速够，冲击细节勉强 |
| **200Hz（云端 RTS 推荐）** | 16B | \~96 KB | 覆盖 100Hz 带宽，泵压/落地冲击保真 |

- **云端双向滤波（RTS）用 200Hz**：姿态解算主频 <10Hz（100Hz 够），但要保住落地冲击/泵压细节需 200Hz（奈奎斯特 100Hz）。与架构文档 §11 的 200/400Hz 评估一致。
- **压缩必做**：IMU 原始序列冗余高，zlib 2–3×，ESP32 有算力。
- **月流量**（只传中间段 + 压缩，200Hz≈40KB/圈；一天 3 人×50 圈×26 天）≈ **156 MB/月** → **DTU 300M/月套餐够用有余**。不压缩(390MB)会超，故压缩是硬要求。

> 结论：**流量维度 300M/月足够（前提：只传中间段 + 压缩）。**

## 2. 端到端延迟（"开火车"20 人并发）—— 卡点在串口

链路：`Tag → ESP-NOW → 基站 → TTL串口 → 4G DTU → 云 → 手机`

| 段 | 速率/延迟 | 是否瓶颈 |
|-|-|-|
| Tag → 基站（ESP-NOW 2.4G） | <10ms/包；20 台竞争同信道但占用率低（\~1-2%） | 否（需发送错开/退避） |
| **基站 → 4G DTU（TTL 串口）** | **模块实测上限 460800 ≈ 46 KB/s 有效** | **★是，主瓶颈** |
| 4G DTU → 云（Cat.1 上行） | \~5Mbps=625KB/s；受串口喂入速度限制 | 否 |
| 云 RTS 解算 | 单圈 <1s，并行扩容 | 否 |
| 云 → 手机（WS/MQTT 推送） | 100–300ms | 否 |

**串口段实测（460800）**：

| 上传内容 | 数据量 | 串口耗时 | 端到端 |
|-|-|-|-|
| ❌ 20 人整圈详细数据**同时**传 | 20×40KB=800KB | \~17s | \~18s（不可接受作实时） |
| ✅ 20 人**实时摘要**（双流分离） | 20×\~50B=1KB | <0.1s | **秒级看到圈速** |
| ✅ 详细数据错峰补传（后台） | 800KB | \~17s 陆续 | 用户无感（不阻塞反馈） |

> 结论：**460800 够用，前提是"双流分离"**——实时摘要秒级，详细数据后台 \~17s 陆续补齐（单基站）。

## 3. 双流分离（核心架构，必做）

Tag 终点过线后分两条流：

| 流 | 内容 | 大小 | 时效 | 走向 |
|-|-|-|-|-|
| **实时流** | 圈速 + 姿态摘要（最大倾角/腾空次数/泵压评分等特征） | 几十\~几百字节 | **秒级** | 立即 ESP-NOW→基站→4G→云→手机 |
| **详细流** | 整圈 200Hz 原始 IMU 段（起点→终点）+ 压缩 | 几十 KB | 可延迟几十秒\~几分钟 | Tag flash 缓存 → 错峰/排队补传 → 云端 RTS 分析 |

**要点**：

- 实时流让教练/学员**秒级看到成绩**，与详细数据传输解耦。
- 详细流**不追求"骑完立刻全到"**，错峰补传即可；供云端事后跑高质量 RTS + 特征分析。
- 这把"20 人同时传大数据"的前提本身消解掉——**比多基站分流更本质**。

## 4. 多基站（规模优化，非必需）

### 4.1 澄清一个误区：整圈数据无法按"起/终点点位"切分

- 一整圈 IMU 数据**只在终点过线那刻才完整**（起点过线时这圈刚开始，无数据）。
- 所以"起点基站传前半、终点基站传后半"**不成立**——起点基站手里没有该圈骑行数据。
- **点位分流（按 exciter_id）只对"过线事件（几十字节时间戳）"有效，对"整圈大数据"无效。** 大数据全压在"终点侧基站"。

### 4.2 分配的正解：queue 深度择空投递（最短队列均衡）

不是中心调度，是分布式反馈：

```
① 每基站周期广播心跳(~5Hz)：{ station_id, queue_depth, queue_max }
② Tag 监听所有基站心跳，维护 depth 表
③ Tag 发详细流时，选 depth 最小的基站 → ESP-NOW 单播（指定 MAC）
④ 基站入队/上传后，下次心跳 depth 更新 → 闭环反馈
```

- **为何优于 RSSI 就近**：queue 深度=真实负载；信号最强≠最闲。
- **必须防羊群效应**：20 个 Tag 可能同时看到"B 最空"→ 一窝蜂投 B 压垮它。缓解：

  - **power-of-two-choices**：在最小的前 2 个里随机挑一个（接近最优 + 天然防羊群）；
  - 心跳/选择加**随机抖动**；depth 相近时按 RSSI 兜底。
- **代价**：Tag 需改**单播**（动态 `esp_now_add_peer` 选中基站 MAC）；协议加"基站心跳"包；单播需 ACK/重试；选中基站掉线要回退广播/次优。

### 4.3 多基站的时间戳匹配（跨基站计时）

- **基站之间不需要时钟同步**——因为时间戳是 **Tag 端锁存**（决策 A2）。
- 圈速 = `t_finish − t_start`，两个时间戳都来自**同一 Tag 时钟**，天然可减，**不管被哪个基站转发**。
- 云端按 **`tag_id` 聚合**、按 **`(tag_id, seq)` 去重**（覆盖重叠时同包多传）、按 **`exciter_id`** 判断过的是哪条线（认线靠激励器码，不靠基站）。

## 5. 演进路线（从单基站到多基站）

| 阶段 | 方案 | 何时上 |
|-|-|-|
| **P1（阶段一）** | **单基站 + 双流分离 + 串口 460800 + zlib 压缩** | 现在。实时摘要秒级，详细数据 \~17s 补齐，够用 |
| **P2** | 多基站 + **queue 心跳择空投递（power-of-two-choices 防羊群）** + 云端 (tag_id,seq) 去重 | 人数/规模上去、单基站补传嫌慢或覆盖不足时 |
| **P3** | 场地大时按覆盖分区部署；每基站独立 4G，串口/空口带宽随基站数线性扩展 | 大场馆/多点位 |

## 6. 对固件/云端开发的硬约束（落地清单）

**Tag 固件（`tag/main/`）**：

- [ ] 双流分离：过线即发实时摘要包；整圈原始段存 flash，错峰补传。

- [ ] 详细流 zlib 压缩后再发。

- [ ] （P2）监听基站心跳表 + 最短队列择空 + 单播 add_peer + power-of-two-choices。

**基站固件（`base/main/`）**：

- [ ] 串口波特率配 **460800**（模块上限）。

- [ ] `cloud_4g.c`：DTU 透传（TTL 3.3V），或裸模组 PPP + 长连接/MQTT；**批量/长连接，不逐包 HTTP**。

- [ ] 断网 SPIFFS 缓存 + 恢复补传。

- [ ] （P2）广播 queue 深度心跳（`uxQueueMessagesWaiting()`）。

**云端（SCF）**：

- [ ] `process-crossing`：按 tag_id 聚合、(tag_id,seq) 去重、exciter_id 认线。

- [ ] RTS 双向滤波用 200Hz 原始段（详细流）。

- [ ] 实时流与详细流分别入库（实时出圈速，详细供分析）。

> ⚠️ 本文数字为工程估算：串口 460800 实际有效速率、DTU 透传时延、ESP-NOW 20 台竞争丢包率、zlib 压缩比，**都需上板实测后回填**，再据此确认是否需要提前上多基站。

# 七、风险与修正建议（审查）

> 本节是对上文方案的第一性原理审查。**架构思路（双流分离 / 时间戳 Tag 端锁存 / queue 择空均衡）是对的、专业的**，保留。以下是会翻车的瓶颈与修正。

## 7.1 🔴 硬瓶颈

### R1. 串口 460800 错峰补传，在**连续运营**下会永久积压（最大隐患）

- 上文「20 人一波 800KB → 17s 补完」是**一波打完再无人**的理想值。真实泵道是**连续来人**。
- 稳态吞吐：串口有效 460800 ≈ **46 KB/s**，压缩后 \~40KB/圈 → **每秒只能吐 \~1.15 圈**的详细数据。
- 若详细流**产生速率 > 46 KB/s**（密集"开火车"瞬时远超），base flash 队列**只增不减** → 补传延迟从"几十秒"劣化到"几分钟→几十分钟→flash 塞满丢数据"。
- 上文 §6 让 base 存 flash 缓存，但**没算稳态吞吐 vs 产生速率的平衡**，也没定"队列满丢哪个"。**这是整个补传方案成立与否的关键。**

### R2. 成品透传 DTU 下，"批量/长连接不逐包 HTTP"这条**做不到**

- 选型是 S710Cm **透传** DTU（串口进、透传出的黑盒）。ESP32 只能往串口写字节，**连接方式/协议由 DTU 的 WEB 配置决定**，固件层控制不了"长连接 vs 逐包"、更**无法优雅分块 HTTP POST + 续传**。
- 与"大 log 用 HTTP 分块上传"的想法冲突：透传模式只有一条固定通道硬塞。

## 7.2 🟠 被低估的风险

- **R3. ESP-NOW 单包 250 字节 vs 详细流几十 KB**：一圈要拆 \~200 个 ESP-NOW 包 + 逐包 ACK/重试。20 台同时补传→空口被几千小包淹没，与 §2「占用率 1-2%」矛盾（那是只发摘要时）。
- **R4. zlib 在 Tag 上的耗时/内存/压缩率未评估**：压 96KB 需 \~32KB 字典 RAM + 数百 ms，和实时任务抢 CPU/RAM；且**直接 zlib 压缩率一般，需先 delta 编码**才好压。
- **R5. 详细流数据源应为"触发有效区间"而非"整圈"**：双向滤波只需过起点→过终点的有效区间数据，比"整圈 200Hz"更少，可进一步减量。

## 7.3 ✅ 修正建议（按优先级）

> **需求修正（关键）**：详细流**必须实时上云**（跑完这圈马上做双向滤波 AI 分析 + 虚拟赛道回放，不能事后导）；且骑手**串行开火车、相隔 3-5m、不肩并肩（不是同时并发）。基于此重算——4G 实时补传可行，前提是压缩把每圈压到 ≤24KB**。

**重算（串行 + 压缩）**：开火车相隔 \~4m @ \~5m/s → 每 **\~0.8s 来一圈**详细流（串行，不是同时爆发）。串口有效 \~56KB/s。

| 每圈详细流 | 产生速率 | vs 串口56KB/s | 单圈传输 | 结论 |
|-|-|-|-|-|
| 200Hz 原始不压 94KB | 120KB/s | 超 | 1.7s | ★积压 |
| **200Hz + delta+zlib(4x) ≈ 23KB** | 30KB/s | **裕量1.9x** | 0.4s | **✅ 不积压，实时跟得上** |
| 100Hz + 压缩 ≈ 12KB | 15KB/s | 裕量4.5x | 0.2s | ✅ 更宽松 |

**修正建议（按优先级）**：

1. **详细流走 4G 实时补传（满足"马上看"）**，但**压缩是硬门槛**：只传触发有效区间 + **delta 编码 + zlib**，把每圈压到 **≤24KB**（200Hz）或 ≤12KB（100Hz）。达标则串行开火车下**每圈 0.4s 传完、间隔 0.8s，稳态不积压**。
2. **两个用途分级**：① AI 分析要"跑完马上看"→ 详细流**优先队列、过线后立即发**；② 虚拟赛道回放"可不马上但别迟"→ **普通队列**，AI 流传完的间隙补，flash 兜底保证最终必达（不丢）。
3. **数据源 = 触发有效区间**（起点→终点），不是整圈——进一步减量。
4. **ESP-NOW 分片(R3)是真开销**：一圈 23KB 拆 \~95 个 250B 包；串行下同一时刻通常只 1 个骑手在传，空口不挤（比"20台同时"好得多）。仍需实测丢包/重传。
5. **上板实测优先级**：① Tag 上 delta+zlib 实际压缩比（**能否稳定 ≤24KB/圈**，这是方案成立的命门）② 透传 DTU 长时稳定吐 \~56KB/s ③ ESP-NOW 单骑手 23KB 分片传输耗时+丢包 ④ base flash 队列在最坏间隔（骑手挤到 2-3m）下的短时增长。

## 7.4 一句话

架构方向正确。在**串行开火车（相隔3-5m、不肩并肩）**约束下，详细流**4G 实时上云是可行的**——命门是**压缩**：把每圈触发区间压到 **≤24KB（200Hz，delta+zlib）**，则每圈 0.4s 传完 < 间隔 0.8s，串口 56KB/s 有 1.9x 裕量，稳态不积压，满足"跑完马上看 AI 分析"。若压不到（>48KB/圈）则会积压，需降到 100Hz 或提前上多基站。**先实测压缩比——这决定成败。**（此前"走 WiFi/USB 事后导"建议不满足"实时看"需求，已修正。）  ⚠️ **本节 §7 的 460800、23/24KB 等数字已被 §八 实测校验取代——以 §八 为准（串口实为 921600，每圈压缩后 ≤20KB）。**

# 八、实测校验（修正，以本节为准）

> **本节用真实飞行 log + 真实压缩测试的数据，取代前文 §1/§2/§7 中基于估算的数字**（尤其"串口上限 460800"「94KB/圈」——前者是误判、后者是高估）。以下均为实测。

## 8.1 两处更正

- **串口厂商上限 = 921600，不是 460800**。依据：DTU 指令手册「8、设置串口参数命令」明确 **TTL 波特率 1200\~921600**。前文多处写的 460800「模块上限」是错误前提，作废。串口理论 921600 ≈ 90KB/s，**50% 降额 = 45KB/s 系统可用上限**。
- **每圈数据量按实测重估**，见下。

## 8.2 实测 log（LIKLOG1 格式）

一个真实 log：**30.6KB / 19.7s**，头标称 100/25/50Hz，**实际录到 IMU 45Hz + BARO 22Hz + RESULT 22Hz**。

- 构成：IMU 15KB + BARO 5.7KB + **RESULT 10.6KB**。
- **双向滤波只需 IMU+BARO 原始（RESULT 是解算结果，云端自己重算，不传** → 省 1/3）。需传原始 ≈ **1.05 KB/s**。

## 8.3 压缩（能做，实测有效）

在该 log 上实跑：

| 方案 | 压缩率 |
|-|-|
| 直接 zlib(9) | 1.82x |
| **IMU delta 编码 + zlib** | **2.66x**（推荐；IMU 连续信号差分后更好压） |

ESP32 有 zlib 算力，压缩可做。

## 8.4 每圈数据量（骑手 25-50s，delta+zlib 2.66x）

| 圈长 | 原始 IMU+BARO | **压缩后** |
|-|-|-|
| 25s | 25.7 KB | **9.7 KB** |
| 30s | 30.8 KB | **11.6 KB** |
| 40s | 41.1 KB | **15.5 KB** |
| 50s（最长） | 51.3 KB | **19.3 KB** |

**规划值：每圈按 ≤20KB（压缩后，覆盖最长 50s 圈）。**

## 8.5 链路能力核对（921600，50%降额=45KB/s）

| 场景 | 计算 | 结论 |
|-|-|-|
| 常规间隔 0.8s（开火车 4m@5m/s），50s圈 19.3KB | 24 KB/s | ✅ 满足 50% 余量 |
| 极限贴车 0.4s（2m），50s圈 19.3KB | 48 KB/s | ⚠️ 略超，flash 缓冲吸收 |
| 单圈传输时间 | 19.3KB / 45KB/s = 0.43s < 0.8s | ✅ 稳态跟得上 |

## 8.6 结论（现有硬件够用）

- **现有单基站透传 DTU 就够（当前配置 230400；带宽紧张可实测升到 921600）**：只传 IMU+BARO 原始 + delta+zlib（实测 2.66x）→ 每圈 ≤20KB，常规间隔下 24KB/s，满足 200Hz→45Hz 采样下的实时补传 + 50% 余量。**不需换裸模组、不需双基站、不需打 PCB。**
- 仅"50s 长圈 + 极限贴车 0.4s"短时略超，flash 队列吸收即可（决策 17c 缓存补传）。
- ⚠️ **前提**：本 log 采样为 **45Hz**。若为保落地冲击细节拉到 100/200Hz，数据量按倍数放大（100Hz≈2×→每圈压缩后 \~22-40KB），届时需更狠压缩或双基站——**采样率一旦确定，按 8.4 的 B 方案线性缩放即可重算**。

## 8.7 落地清单更新
