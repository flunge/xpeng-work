# 二、服务器架构的流程说明

## 1、设备使用TCP/MQTT连接服务器

TCP MQTT协议可以使用环境监控，数据采集，设备控制，实时控制，等全部场景流程是：4G设备先通过MQTT连接设备管理服务器。当用户使用小程序/WEB后台控制设备的时候，先用发一条命令到业务服务器，业务服务器收到命令后，转发给设备管理服务器，设备管理服务器在转发给具体的设备。反之设备上报或者应答 与服务器控制流程相反。

如果需要实时通讯的场景，比如扫码支付，就需要用TCP或者MQTT协议。

## 2、设备使用HTTP(S)连接服务器

HTTP协议一般使用环境监控等只上报状态，不设置参数或者设置参数不频繁，不需要实时操作的情况。可以实现低功耗等场景。

HTTP服务器一般并发性都比较大也很成熟了，所以设备一般可以直接使用HTTP协议上报给业务服务器。

比如 水表每天采集4次数据上报。大棚2分钟上班一次温度数据等。

# 三、服务器特别的注意事项

## 1、什么是服务器

所谓服务器的不只是一台电脑，是一台具有公网访问能力的电脑（一般小公司局域网是不行的，那种专网卡的大公司和团体的基站内网除外），并且还具有管理设备接入能力和业务数据处理的软件系统。这种一般需要专门的服务器开发能力的工程师开发才行。大部分情况下可以去阿里，腾讯，华为等上面去购买ECS服务器搭建。现在自己建机房的已经很少了。

## 2、对不清楚TCP和MQTT协议的开发人员建议

对于熟悉开发小程序和WEB服务器业务的开发人员，一般不熟悉设备管理服务（器）。这个需要考虑并发性和大量设备的稳定性，还要熟悉TCP和MQTT协议。能力强的公司的可以自己搭建部署，这个节约成本，MQTT协议推荐开源的EMQTT服务器，可自行百度；能力弱的可以使用银尔达IOT，阿里IOT，移动onenet，华为IOT等第三方平台的设备接入平台。然后设备管理服务（器）与自己的业务服务器使用HTTP等协议调用服务器API对接即可，可以安全，快速的对接大量设备，但是成本高（第三方平台一般需要收费，具体联系对应的供应商）。

## 3、设备管理服务器的实现语言

设备管理服务器与实现服务器的语言技术没关系，用Java，go, C ，python什么的都没关系，只要是TCP或者MQTT协议的服务器即可。

## 4、设备服务器如何管理设备

设备连接服务器，就涉及到设备管理问题，管理设备重点在于区分设备，一般需要用一个唯一的标识。4G设备推荐使用模块的IMEI（15为字符串）码来管理，如果是正常的模块，理论在全球都是唯一的。TCP协议可以使用注册包，第一次连接服务器的时候就上报这个连接的设备IMEI，就可以把链接与设备对应，直到断开之前基本都有效。MQTT协议一般使用ClientID为IMEI，然后topic里面包含IMEI变量，做设备区分，比较方便。

设备在平常工作的时候，可以周期发数据给服务器，服务器检查是否有收到数据，如果超时没收到数据了，基本就可以认为设备异常，可以断开连接，处理异常逻辑，然后等设备恢复上线。设备可以周期1-2分钟给服务器上报数据，服务器可以超时2.5倍上报时间，如果都没收到任何数据，基本可以认为设备异常，这个方法简单有效，建议设计的时候考虑进去。

## 5、系统稳定性设计的说明

整个系统设计稳定并不容易，服务器要做完稳定不简单，并发性，安全性，稳定性，根据客户需求评估，没有研发能力的客户，其实找谁都能做。如果没有供应商可以找银尔达推荐服务器平台供应商对接，省事，省力，靠谱。供应商靠谱是最关键，能提供专业的建议，遇到问题能及时修复解决，遇到很多客户项目半途而废，终止的项目，很大一部分原因是供应商不行。

## 6、系统异常排查方法的建议

在测试阶段，一般客户会直接用DTU连接自己的服务器，然后发现设备连接不上。这种一般要么是DTU参数错了，要么是服务器本身有问题。典型的错误就是用自己公司的电脑本地部署了TCP或者MQTT服务器,还有就是服务器端口没开放。

测试流程，先不用DTU测试，用不在一个局域网的电脑客户端连接自己的服务器，看是否能连上，如果能连上，可以证明服务器没问题。然后再把服务器的参数给技术工程师，让他测试一下服务器是否正常，如果都正常，基本上检查DTU的配置参数是否正确，是否更新。

在量产阶段，对于设备来讲，通过目前经验来看，只要保证供电稳定和信号环境正常和基本的心跳通讯周期，绝大部分情况下都很稳定，超过100W+的设备和2W+的企业客户在使用验证。所以当服务突然大批量离线或者无法控制的时候，基本都是服务器问题或者SIM卡过期或者流量问题。当局部某几个设备异常，一般先检查SIM卡状态，如果能拍20秒LED视频看设备状态，才能排查

## 7、服务器能否远程控制设备重启

首先是能。一般在想及时更新参数的时候的时候使用（DTU固件）。但是大多数情况下是不需要发命令控制DTU设备重启的。因为如果DTU异常的情况，基本上也是连不上服务器的，无法通讯的，DTU是不需要重启的。所以基本上只有想快速更新参数的时候才会用到。

实现的方法有2种，

1、基本参数里面要先开启"远程控制"功能,然后设备连接的服务器可以发送config,set,reboot\r\n命令重启设备，如果没提前开启，是不能执行的。

2、使用任务或者数据模板实现，在代码里面解析自定义的命令数据，满足条件后调用重启API，重启设备即可。

3、根据这个原理，其实服务器可以执行全部的config命令控制和配置设备参数，或者使用任务可以实现任何数据解析逻辑处理。比如控制继电器全开，全关；比如控制继电器的时候播放对应的语音等。

## 8、4G设备支持的协议说明

4G DTU /RTU 与服务器 之间使用网络进行通讯，一般可以是协议有TCP，MQTT，HTTP等协议。

设备与 4G DTU之间使用串口进行通讯，一般可以是Modbus RTU协议，电力协议，环境，水质协议或者自定义的串口协议。

DTU透传的意思就是服务器 TCP或者MQTT协议发送设备需要的命令，然后DTU把收到的数据原封不动的转发给串口，如果自己的串口设备收到命令后产生了应答，DTU 就把串口收到的数据通过网络协议原封不动的传给服务器，这样就完成了透传。

DTU除了透传，还可以利用任务或者数据模板，做数据清洗，数据解析，自定义控制逻辑等，详情可以参考相关资料。比如设备是modbus协议的转换成json后给服务器。比如设备是DL645协议，需要自动采集后，周期上报给服务器。

不清楚网络协议和设备协议的关系。当问到4G模块是否支持modbus RTU协议，DL645，HJ212协议的的问题，答案是支持的。因为网络协议和串口协议支持传送任何数据，这些协议只是其中的一种特殊格式而已。只是如果客户需要解析这些数据格式的具体内容或者按某一个国标规范（比如HJ212协议）组装上报到服务器的时候，需要使用任务来处理，这种可以直接找银尔达工程师处理。
